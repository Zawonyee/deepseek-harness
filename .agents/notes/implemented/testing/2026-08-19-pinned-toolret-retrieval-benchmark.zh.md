# Agent Note: 固定版本的 ToolRet 工具检索评测

Status: implemented

[English](2026-08-19-pinned-toolret-retrieval-benchmark.md) | 中文

## 问题

动态能力组合实验目前还没有具有代表性的公司任务流。只使用手写的 Harness 提示词做度量，会让结果与原型自己的词汇相互耦合，很容易人为制造有利结果；一开始就做端到端执行，则会把检索质量与工具可用性、参数生成、权限和运行时失败混在一起。仓库也不能悄悄内置一个汇集多个来源、却未声明统一数据许可证的公开数据集。

## 决策

仓库在 [`scripts/toolret`](../../../../scripts/toolret/README.zh.md) 下提供本地 ToolRet 检索评测通道。它把作者发布的工具仓库与查询仓库固定到明确的 revision，固定每个 Parquet 对象的大小和 SHA-256 摘要，把全部数据下载到被忽略的 `.cache/toolret/` 树，并在外部数据进入评测器之前完成校验。适配器会保留上游仅含 instruction 的查询，而且只会归一化嵌在其他方面有效的标签 JSON 中的 Python 风格非有限数值字面量。

首个基线是在合并后的 44,453 个工具语料上运行的进程内倒排 BM25 索引。它会分别在不带和带 ToolRet 任务 instruction 的情况下评测 7,961 条查询，报告该评测集在 5、10 和 20 截断位置的 `NDCG`、`MAP`、`Recall`、`Precision` 与 `Comprehensiveness`，并输出包含源 revision 和选择元数据的带版本 JSON。该通道属于评测工具，而不是产品 package：它不会注册 Harness 工具、改变会话循环，也不会创建运行时安装机制。

## 曾考虑的替代方案

**把 ToolRet Parquet 文件内置进仓库。** 这会让首次使用无需联网，但也会把二进制数据加入 Git，并暗示一种统一数据集卡并未授予的重新分发立场。带内容摘要的固定版本下载器既能实现可复现性，又不会把数据当作项目源码。

**从端到端工具执行评测开始。** MCP-Atlas 或内部回放以后可以一起检验选择、参数生成、权限和结果，但这些变量会掩盖初始能力路由器是否检索到了正确工具。检索是更小、可证伪的问题。

**只使用合成的 Harness 工具 schema。** 合成任务适合确定性的单元测试，但规模太小，而且与实现共享过多词汇，无法支撑继续或停止的决策。它们继续作为适配器和指标正确性的 fixture，而不是评测语料。

**把评测做成工作区 package。** 在任何检索设计尚未证明值得获得产品所有权之前，package 会暗示一个受支持的运行时或库边界。根目录脚本可以保持实验可复现，同时不扩大已发布 package 图。

## 后果

实验现在有了一条公开、固定、不需要模型密钥的基线，可以在笔记本电脑上重跑，并与未来的任务条件路由器比较。仅 query 与 query 加 instruction 两组结果共享同一个数据适配器和评测器，因此改进不能来自运行之间更换语料或指标实现。提交到仓库的单元测试覆盖源固定、畸形数据行、上游 `NaN`、仅含 instruction 的查询、确定性排序和指标计算。

该通道只衡量公开数据上的检索相关性。它不能证明公司流量具有相同分布、选中的工具能够成功执行、运行时变更是安全的，也不能证明神经检索器复现了 ToolRet 的公开结果。首次使用需要联网，完整运行会消耗本地 CPU 时间，任何重新分发或更广泛的数据使用仍需要审查底层数据集条款。
